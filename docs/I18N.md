# Language options (i18n)

The citizen-facing app is available in **English** (default) and **Hindi** (हिन्दी). It is built with a
tiny in-house layer (no dependencies) in `smart-garbage-frontend/src/i18n/` so more regional languages
can be added by dropping in one JSON file.

> **IMPORTANT - native review required.** `hi.json` is a first draft written to be simple, natural
> civic-service Hindi, but it has **not** been reviewed by a native speaker. A native Hindi speaker (ideally
> someone from the municipality's own communications team) must review it before launch. The same applies
> to every future language.

## Scope

| Area | Translated? |
| --- | --- |
| Header, footer, language switcher, theme toggle, 404, error boundary, loading text | Yes |
| Auth: Login, Register, Forgot password, Reset password | Yes |
| Citizen: Dashboard, Report form (incl. map picker and validation messages), My Complaints, Complaint details | Yes |
| Officer: Dashboard, Assigned complaints, Map, Profile | Yes |
| Status / urgency / category labels | Yes (display only) |
| **Admin screens** (`src/pages/Admin/**`) and the admin links in the navbar | **No - English for now** |
| Messages returned by the API (shown in toasts / alerts) | **No - see limitation below** |
| Complaint titles, descriptions, officer comments, area/ward names (user data) | No (shown as stored) |
| The brand name "Smart Garbage System" | Kept in English everywhere |

## How it behaves

* The default is always **English**. The app does **not** guess from `navigator.language`; only an explicit
  choice in the switcher changes it.
* The `<select>` in the navbar (next to the theme toggle, also visible when logged out) stores the choice in
  `localStorage` under `sgs-lang` and sets `<html lang>`. If storage is blocked the choice is kept in memory only.
* Status and urgency **values** stay English internally (`in_progress`, `high`, ...). They are what the API and
  database use and what the `status-<value>` CSS classes key on. Only the displayed label is translated.
* Dates use `Intl` with the active language (`formatDate` / `formatDateTime`). English deliberately uses the
  browser's default locale format so the English UI is unchanged from before i18n; Hindi uses `hi-IN`.
  Numbers use `formatNumber` (`en-IN` / `hi-IN`, Latin digits).

## Using it in code

```jsx
import { useTranslation } from '../../i18n/LanguageContext';

const { t, lang, setLang, languages, formatDate, formatDateTime, formatNumber } = useTranslation();

t('citizen.dashboard.welcome', { name: user.name }); // "Welcome, {name}!"
t('some.key', { count: 3 });                         // plurals: some.key_one / some.key_other
```

* `t(key)` falls back: current language -> English -> the key itself. In development a missing key logs one
  `console.warn` per key.
* `useLanguage()` is an alias of `useTranslation()`. Without a `LanguageProvider` (e.g. an old unit test) you get
  English, so existing tests do not need the provider.
* Helpers in `src/i18n/labels.js`: `statusLabel(t, status)`, `urgencyLabel(t, urgency)`, `categoryLabel(t, value)`.
  `categoryLabel` returns the same text as `formatComplaintCategory` in English, which the admin pages still use.
* Validation errors are stored as keys and translated at render, so they follow a language switch.
* For unit tests: `import { renderWithI18n } from '../../test-utils'` then
  `renderWithI18n(<Thing />, { lang: 'hi' })`, or wrap with `<LanguageProvider initialLang="hi">`.
* Do not put `t` in a `useEffect` dependency list that triggers network calls or map rebuilds; read it through a
  ref (see `Officer/Map.jsx`, `MapPicker.jsx`) so switching language never re-fetches or resets the map.

## Adding a language (e.g. Marathi `mr`)

1. Copy `src/i18n/en.json` to `src/i18n/mr.json` and translate the **values**. Keep every key and every
   `{placeholder}` exactly as in English.
2. Register it in `src/i18n/languages.js`:
   ```js
   import mr from './mr.json';
   ...
   { code: 'mr', label: 'मराठी', locale: 'mr-IN', dateLocale: 'mr-IN', catalog: mr },
   ```
3. Run `CI=true npx react-scripts test --watchAll=false`. The parity test (`i18n/__tests__/catalogParity.test.js`)
   automatically checks the new catalog. The language appears in the switcher with no other change.
4. Ensure the font stack renders the script (Devanagari already works with system fonts; for other scripts
   check the screenshot on Windows, Android and iOS) and have a native speaker review the file.

## Key naming rules

* Nested JSON, dotted keys, grouped by area: `common.*`, `nav.*`, `footer.*`, `auth.*` (`auth.login.*`,
  `auth.register.*`, ...), `status.*`, `urgency.*`, `category.*`, `citizen.dashboard.*`, `citizen.form.*`,
  `citizen.tracker.*`, `citizen.details.*`, `officer.*`, `notFound.*`.
* `camelCase` for the last segment, except `status.*` and `category.*`, which use the exact API value
  (`status.in_progress`, `category.food_waste`) so labels can be looked up from data.
* Put a string in `common.*` only if two or more screens share it; otherwise keep it with its screen.
* One sentence per key; never concatenate translated fragments (word order differs between languages). Use
  `{placeholders}` for names and numbers.
* Plurals: add `key_one` and `key_other` (plus `_zero`/`_two`/`_few`/`_many` if the language needs them) and call
  `t('key', { count })`.
* Never translate API values, route paths, CSS classes or data attributes.
* Status labels used in badges are lower-cased by code because the badge CSS capitalises them; write
  `status.*` in normal title case.

## Parity test

`src/i18n/__tests__/catalogParity.test.js` fails if any non-English catalog:
* lacks a key that exists in `en.json`, or has a key that `en.json` does not have;
* has an empty value;
* has a different set of `{placeholders}` than the English string.

Also covered by tests: `translate.test.js` (fallback, interpolation, plurals, warn-once),
`LanguageContext.test.js` (persistence, `<html lang>`, blocked storage), `LanguageSwitcher.test.js`
(header switches to Hindi and back) and `Dashboard.hi.test.js` (citizen dashboard in Hindi).

## Known limitations

* **Server messages stay in English.** Text returned by the API (`error.response.data.error`, the success
  `message` after submitting a complaint, email content, etc.) is shown as received. Only the app's own fallback
  messages (used when the server sends none) are translated. Fixing this needs the API to return error codes or
  to honour an `Accept-Language` header; the frontend would then map codes to `t()` keys.
* Admin screens are English only, as are the admin navbar links.
* The pagination buttons' hidden screen-reader text ("First", "Next", ...) comes from react-bootstrap and is not translated.
* The Leaflet map's own attribution/zoom controls are English.
